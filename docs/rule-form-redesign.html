Reward Rule Form — Field Audit & Redesign

Examining each field in the current rule form against the dual-unit architecture

Field-by-Field Audit
FieldCurrentBackend UsageVerdictReason
Name Free text Stored as rule.name, shown in admin lists KEEP Essential for identification
Rule Type
Earn / Burn / Bonus		 Dropdown (3 options) Always stored as "reward". Backend ignores the distinction. REMOVE "Burn" = redemption (separate flow). "Bonus" = same as Earn with different event_type. Hardcode to "reward".
Event Type
order.completed, review.submitted		 Dropdown config.event_type — matched against incoming events in evaluate_rules KEEP This is what differentiates rules. Critical.
Conditions
Field / Operator / Value		 Dynamic rows config.conditions[] — evaluated by check_conditions. Supports: payment_method, order_amount, is_cod, is_first_order, collections, customer_tags KEEP Powerful targeting. But should show friendly field names instead of raw field IDs.
Bucket Type
loyalty_points / cashback / gift_card_credit		 Dropdown (3 options) config.action.bucket_type → parsed by parse_bucket_type. For non-COD: uses this value. For COD: overridden to CodPending. REMOVE With dual-unit, all reward rules produce earned_credit. Gift cards are issued separately. "loyalty_points" and "cashback" are the same bucket. Hardcode to "earned_credit".
Calculation
percentage / fixed		 Dropdown config.action.calculation — "percentage" multiplies by order_amount, "fixed" gives flat value KEEP Core mechanic. "5% of order" vs "flat 50 points".
Value Number input config.action.value — percentage (5.0) or fixed amount (50.0) in earning_unit CHANGE Keep the field but clarify the unit. For percentage: "5" means 5%. For fixed: should show "50 ★" not "50" — make it points-aware.
Max Amount Number input config.action.max_amount — caps earning_unit for percentage rules. Only applies to percentage. CHANGE Keep but only show for percentage rules. Label should say "Max ★ per order" not "Max Amount".
Conversion Rate Number input config.action.conversion_rate — multiplied with earning_unit to get currency_equivalent REMOVE Now set at merchant level in Settings → Points Configuration (points_to_currency_rate). Per-rule override is confusing and inconsistent. Hardcode to 1.0 — the merchant rate handles conversion.
Expiry (days) Number input config.action.expiry_days — sets expires_at on ledger entry KEEP Important for point lifecycle. "Points expire in 90 days".
Summary: Remove 3 fields (Rule Type, Bucket Type, Conversion Rate). Keep 5 fields (Name, Event Type, Conditions, Calculation+Value, Expiry). Change 2 fields (Value label, Max Amount conditional visibility). Net: 7 fields down from 10, and much clearer.

Key Changes
#ChangeWhy
1Remove "Rule Type" dropdown (Earn/Burn/Bonus)Backend only has "reward". Burn = redemption flow. Bonus = same as Earn with different event.
2Remove "Bucket Type" dropdownAll reward rules → earned_credit. Gift cards are separate. No merchant choice needed.
3Remove "Conversion Rate" fieldSet globally in Settings → Points Configuration. Per-rule override creates inconsistency.
4Rename "Event Type" → "Trigger Event" with friendly labels"order.completed" → "Order Completed". Less technical.
5Conditions: show friendly field names in dropdown"order_amount" → "Order Amount", "is_first_order" → "First Order" etc.
6Value shows unit suffix: "%" for percentage, "★" for fixedNo ambiguity about what "10" means.
7Max Amount only visible for percentage rules, labeled "Max per order ★"Doesn't apply to fixed rules. Unit clarity.
8Add live previewShows real example: "On ₹1,000 order → 100 ★ (₹25) · capped at 200 ★"
