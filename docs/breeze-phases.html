Breeze — Implementation Plan

Build the Ledger Right,
Ship Features on Top

Seven phases from bedrock to platform. Each phase builds a complete, tested layer. No feature ships on a shaky foundation.

!
Gate rule: Each phase's exit criteria must be fully green before the next phase starts. The 8 ledger truths are tested in Phase 0 and re-validated in every subsequent phase. A regression in any truth is a stop-the-line event.
Service Boundaries
These layers are not built by Breeze. We define the interface contract and consume them. Getting these boundaries wrong creates the band-aid architecture Breeze is designed to avoid.
Internal 1. Identity Service
Owner: Internal identity team
phone → { customer_id, is_verified, is_new }
Opaque dependency. Breeze calls it, doesn't build it. Primary key is phone normalised to E.164. Provisional wallet + identity merge depend on this contract.
Phase 0 — define contract
Internal 2. CPaaS / Notifications
Owner: CPaaS team
send(customer_id, template, variables, channel_hint, locale)
Breeze owns trigger logic, template definitions, and Connector mapping (which vendor). The CPaaS team owns actual WhatsApp/SMS/email delivery.
Phase 2 — integration
External 3. Logistics / Delivery
Owner: Shiprocket / Delhivery
POST /order-delivered { order_id }
Breeze exposes one inbound webhook. We own the state machine after the signal arrives. We do not build delivery tracking.
Phase 2 — webhook receiver
External 4. Payment Gateway
Owner: Out of scope
payment_method read from Shopify order webhook
Breeze is post-payment. No gateway integration. Payment method arrives via Shopify webhook. UPI top-up (Phase 5) uses Razorpay but only for post-payment ledger entry.
Never — out of scope

Bedrock
Ship nothing. Prove the architecture.
⚙ Backend
  • Project scaffold — Rust/Axum, PostgreSQL, Redis, CI/CD, telemetry, type generation
  • Ledger core — all 8 truths:
    • Wallet identity model (merchant-scoped, stable, independent of holder)
    • Bucket type system (earned-credit, cod-pending, gift-card, customer-funded)
    • Four movements: in, held, out, across
    • Atomic triple: earning unit + currency equivalent + conversion rate
    • Full cause tracing: event + rule snapshot + campaign snapshot + actor + timestamp
    • Idempotency key: SHA256(merchant + event + rule), checked before every write
    • Double-entry balancing at write layer (bucket → customer → merchant → system)
    • Two balance queries: displayed (includes held) vs spendable (excludes held)
    • Append-only — no compaction, no overwrites, no background rollups
  • Event system — ingestion, schema validation, dedup
  • Rule engine core — YAML DSL parser, generic interpreter, rule versioning, immutable snapshots, layered inheritance
  • Core DSL resources — WalletPolicy, EventSchema, RewardRule
  • Identity resolution — phone → customer_id contract
◈ Frontend
  • Project scaffold — SvelteKit, foundation module, type generation, API client
  • Design system — CSS custom properties, light/dark theme, token scale
  • Component library — @juspay/svelte-ui-components integration
  • Example module — demonstrates full module pattern (barrel, store, remote, UI)
⚠ Testing — the whole point
  • Property tests — debits = credits, idempotent replays, no mutation, past-timestamp reconstruction
  • Concurrency tests — parallel writes to same wallet, duplicate event floods
  • Rule engine tests — layered inheritance, snapshot immutability
✓ Exit Criteria
  • All 8 foundational truths have dedicated test suites that pass
  • Concurrent write stress test passes without invariant violations
  • Rule engine evaluates a reward chain and produces correct ledger entries
  • Frontend scaffold has one complete module demonstrating the full pattern

  • Customer order → webhook → earn → credit visible in wallet
  • Customer redeems at checkout → ledger debited → Shopify order discounted

Campaigns + Loyalty Tiers
From cashback tool to loyalty platform.
⚙ Campaigns
  • Campaign resource — overlay model, multiplies base rules, never duplicates
  • Time-bounded — activates/deactivates automatically, base rule resumes with zero config change
  • Campaign snapshot — captured at evaluation time (Truth 4)
  • Festive templates — pre-built Diwali / Navratri / Holi configs, multiplier presets
⚙ Loyalty Tiers
  • LoyaltyProgram resource — tier definitions with custom names + thresholds
  • Evaluation criteria — spend, points, or order count (configurable)
  • Auto transitions — upgrade + downgrade on qualifying events
  • Per-tier benefits — earn rate multiplier, exclusive access, etc.
◈ Frontend
  • Campaign builder — template → dates → multiplier, campaign calendar view
  • Loyalty designer — tiers, criteria, benefits configuration, tier distribution analytics
  • Customer-facing — current tier, progress bar, countdown widget, tier benefits
✓ Exit Criteria
  • "Diwali 3x" campaign activates → auto-deactivates → base rule resumes
  • Customer tier auto-upgrades on qualifying purchase, earn rate adjusts
  • Campaign + tier compound correctly (Gold + Diwali 3x = 3x of Gold rate)

Gift Cards + Referrals
Two new value instruments that stress-test every ledger truth.
⚙ Gift Cards
  • GiftCardProgram — DSL resource
  • Bearer instrument — code-identified, transferable until claimed
  • Issuance — single (purchase/admin) + bulk (CSV, idempotent per batch_id + row)
  • Transfer — across movement (bearer → customer wallet on claim)
  • Partial redemption + expiry — out:expired entry, never deletion
  • Cause tracing — payment ref for purchased, admin actor for issued, no rule (explicit null)
⚙ Referrals
  • ReferralProgram — DSL resource
  • Dual reward — referrer + referee, independent entries
  • Anti-fraud — same IP/device, velocity limits
  • Vanity codes — RIYA10, creator/influencer mode
  • Tiered commissions — creator dashboard, Razorpay payout
✓ Exit Criteria
  • Full lifecycle: purchase → issue → send → claim → partial redeem → expiry — all correct entries
  • CSV re-upload produces zero duplicates
  • Referral converts → both earn → fraud signals flag suspicious patterns
