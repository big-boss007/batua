Custom per-tier — five designs (no toggle)

Same goal: let the merchant set caps individually or via a single base × multiplier, without a mode toggle. Five different design philosophies for combining the two entry methods.

1 Mixed always-on  ·  2 Quick-fill action  ·  3 Stepped disclosure  ·  4 Linked-by-default  ·  5 Two-column side-by-side
1Mixed always-on — a "Base cap" input lives above the tier table. Empty tier rows auto-derive from the base; type in any row to override. Both are visible; no mode flip.

Mental model: base first (single source of truth), per-tier overrides as exceptions. Each row defaults to derived; the "Override" link in-place swaps the read-only value for an input. Cleanest when most tiers should follow the formula and only a few need exceptions.

Comparison

DesignDefault mental modelBest forEngineering
1 — Mixed always-onBase sets defaults; type to overrideMerchants who want both visibleLow
2 — Quick-fill actionPer-tier is real; base is a shortcutMostly per-tier work, occasional bulk fillLow–medium
3 — Stepped disclosureBase first, exceptions in-placeMerchants who mostly want the formulaMedium
4 — Linked-by-defaultTiers track the anchor unless unlinkedVisual thinkers; familiar from design toolsMedium–high
5 — Two-columnTwo surfaces, two entry styles, both visibleMerchants who want to see both representationsMedium

My picks: Design 3 (Stepped disclosure) for cleanest mental model — "base first, exceptions inline." Honourable mentions: Design 1 if you want both inputs always visible, and Design 4 if the visual link metaphor resonates with your merchants.
